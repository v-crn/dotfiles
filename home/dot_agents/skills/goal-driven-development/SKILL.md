# 独立レビューと検証でゴールまで進める

統括担当がゴール、許可範囲、依存関係、成果物の統合、最終判定を管理する。一つの子タスクやPRの完成を、全体のゴール達成と扱わない。

Codex・Claude・Geminiなどで共通に使う手順として、特定のモデル、コマンド、サブエージェント機能、永続ゴール機能を前提にしない。このSkill自体はツール、外部操作の許可、自動継続機能を追加しない。

## ゴールと実行条件を決める

1. 現在の依頼、継続記録、作業ツリー、適用されるプロジェクト指示、正本の仕様、関連するIssue・PRを確認し、既存作業を保護する。
2. 目指す状態、対象外、完了条件、必要な証拠、人の判断が必要な条件、外部操作の許可範囲を整理する。既存の指定と許可を引き継ぎ、不足する判断だけを確認する。
3. 独立レビューの実行手段を確認する。利用できない場合は、以下の代替手順を開始時に選ぶ。
4. 既存の作業記録を優先し、なければプロジェクトの文書規則に沿った作業表で追跡する。状態管理ツールがある場合は現在の契約に従う。永続ゴールや自動継続の開始、予算の設定にはユーザーの明示的な指定を必要とし、通常の作業依頼だけで設定しない。未完了の別ゴールを置き換えない。

依頼例と継続記録は [examples.md](references/examples.md) を参照する。

## 担当と独立レビュー

- **統括担当**は成果物と証拠を確認し、全体の完了を判定する。実装を兼任してよいが、担当した成果物の独立レビューは兼任しない。
- **実装担当**には、必要な品質を満たす範囲でコスト・速度・能力の釣り合いがよいモデルを選ぶ。
- **レビュー担当**には、設計・正しさ・境界条件を評価できる高性能モデルを選ぶ。必要な能力を優先し、その条件を満たす利用可能な最新世代を基本とする。ユーザーのモデル指定を優先し、利用できない場合は黙って置き換えない。
- 独立レビューは、主な実装担当とは別のエージェント、別セッション、または人が行う。同じモデルやサービスでもよい。役割名を変えただけの同一担当による自己レビューは含めない。
- モデルを選択できる場合は、実行環境が示す正確な識別子と選択条件に従う。変更できない環境ではその制約を明示する。実際の担当・モデルと選択理由を記録し、不明なモデル名を推測しない。
- 委任時は担当範囲、入力資料、完了条件、禁止する副作用、返す証拠を渡す。独立した実装だけを並列化し、共有ファイルには担当を一人置く。依存する変更は順番に統合する。

自動委任がなければ、[review-briefs.md](references/review-briefs.md) に沿った依頼資料を用意し、別セッションまたは人へ引き渡す。別サービスへの資料送信には既存の許可・情報管理規則を適用する。利用可能な代替が当初のモデル指定やレビュー条件を満たさない場合だけ、条件変更の判断を求める。

レビューを実施できない間は、レビューに依存しない調査・資料準備を進める。依存する実装・完了判定はレビュー待ちとして記録する。レビュー条件をユーザーが変更した場合は、その条件と残る限界を記録し、未実施のレビューを承認済みと扱わない。

## 作業単位ごとに反復する

ゴールを独立した完了条件と依存関係を持つ単位に分ける。既存Issueとの重複を避け、外部への記録が許可されていなければローカルの作業表を使う。

1. **提案する。** 問題、変更範囲、契約、不変条件、検証方法、限界を示す。比較・計測の成功基準は結果を見る前に決める。
2. **提案を独立レビューする。** 正本、現在の実装、完了条件、提案を渡す。下記の判定に従って指摘を解消し、実装へ進む。
3. **実装・検証する。** プロジェクトのテスト方針に従い、必要な境界・回帰テストを実装前に用意する。低影響の変更に実装を写すだけのテストを追加しない。実装、検証、修正を進める。
4. **実装を独立レビューする。** 対象版、実際の差分、検証結果、計画と制約を渡す。指摘を修正し、影響範囲の回帰検証と必要な再レビューを行う。
5. **統合して次へ進む。** 統括担当が実際の成果物と証拠を確認し、親ゴール内の次の実行可能な単位を選ぶ。

### レビュー結果による進行条件

| 判定 | 次の行動 |
| --- | --- |
| 承認可能 | 指定された対象版・範囲について次の工程へ進む。任意改善は採否と理由を記録する。 |
| 修正必要 | 必須指摘を修正し、差分と検証結果をレビュー担当に戻して解消を確認する。不採用とする場合も根拠を照合し、必須でなくなったことを確認する。 |
| 情報不足 | 必要な仕様・資料・検証結果を補って再判定を求める。依存しない作業は続ける。 |

必須指摘への見解が分かれた場合は、正本と再現・検証結果で解決を試みる。新しい証拠なしの議論を繰り返さず、解消できなければ争点、影響、選択肢を示してユーザーに判断を求める。未解決のまま次工程へ進んだり、承認済みと記録したりしない。

契約・設計の重大な変更や、承認後に挙動・権限・不変条件を変える修正は再レビューする。継続レビューは可能なら同じレビュー担当に戻す。変更の影響を受けない証拠は再利用し、同じ内容の重いレビューやテストを理由なく繰り返さない。

## 継続・検証・引渡し

- 途中の補足・修正・進捗確認を既存ゴールへ反映し、進捗には短く答えて作業を続ける。明確な中止や両立しない新目的がない限り、ゴールを置き換えない。中断・再開時には記録と現在の成果物を照合する。
- 同じ失敗では、再実行前に失敗段階と次に得る診断情報を決める。再実行で成功しただけの結果を原因修正の証拠にしない。
- 要件ごとに対象版、成果物、検証、レビュー、残る不確実性を対応づける。過去の成功を変更部分の検証へ無条件に流用せず、有限の計測や合成データを安全性・本番性能の保証と扱わない。
- 並列検証では共有資源の競合を避け、引渡し対象のビルド中はソースを固定する。稼働中の確認環境がある場合は保護し、必要な操作で停止したなら復旧と到達を確認する。
- 人にしかできない操作や未取得の許可が必要なら、依存する作業を止め、確認可能な成果物と必要な操作を示す。独立した作業は続ける。中断時は未完了条件と再開条件を残し、予算切れやレビュー待ちを達成と扱わない。
- 「完了まで続ける」を外部操作の包括的な許可と解釈しない。push・PR作成・マージ・公開などは既存の許可とプロジェクト規則に従い、許可済みの操作を再確認しない。
- 終了前に全完了条件、対象版に対応する証拠、統合状態、文書、引渡し、残作業を確認する。必要な作業が残れば完了にしない。「確認を依頼する」が条件なら依頼まで行い、「承認を得る」が条件なら依頼を送っただけで達成としない。
- 最終回答では成果、検証、重要な限界、必要な人の操作を示す。PR・CI・マージ後の整理が対象に含まれる場合は、そのプロジェクトの手順と必要な証拠に従う。
